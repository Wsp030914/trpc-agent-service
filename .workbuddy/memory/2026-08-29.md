## 对抗性审查：阶段二多后端数据同步（无代码改动）
- 聚焦 Redis→PG Session 迁移、COS Artifact、Qdrant Knowledge、TencentDB Memory、幂等/事务/故障恢复/资源释放。
- 核心缺陷（详见对话报告）：
  1. 【P0】迁移 copy/verify 均未传 WithEventNum，框架 Redis/PG provider 默认 EventNum=1000 → 事件>1000 的会话早期事件静默丢失、verify 截断后一致 → 迁移假 SUCCEEDED。证据：migration/session.go:69,145 GetSession 无 opts；框架 options.go defaultSessionEventLimit=1000；hashidx/service.go ApplyEventFiltering 取末 1000。
  2. 【P0】Redis 读故障被静默当"session 不存在"：框架 checkSessionExists pipeline 错误在 GetSession final hook 被 log.Warnf 吞掉返回 (nil,nil)（service.go:375-395）；copySession 对 source nil 静默跳过（migration/session.go:73-75）；verify 同样盲区 → Redis 故障贯穿迁移窗口时数据丢失但 SUCCEEDED。
  3. 【P1】Qdrant generation 切换无清理：ChunkStatusDeleted/BaseStatusDeleted/DocumentStatusDeleted 只有类型定义无任何删除实现；ScopedKnowledge.Search filter 不含 index_generation → 新 generation active 后旧 chunk 仍 AVAILABLE 持续命中旧版本内容；文档/知识库删除功能整体缺失。
  4. 【P2】verify 事件顺序脆弱：PG getEventsList ORDER BY created_at,id（列 created_at 是写入时间）vs Redis 追加顺序；同 created_at 乱序事件可致 verify 恒失败。summary 导入列 updated_at 用客户端 time.Now()（summary_import.go:126），时钟漂移时被 PG getSummariesList 的 updatedAt.Before(createdAt) 过滤 → verify 失败。
  5. 【P2】knowledge importer 补偿窗口：CreateKnowledgeDocumentAndEnqueue 报错但事务已提交时（响应丢失），DeleteSource 删除 metadata 已引用对象 → 文档 AVAILABLE 但源对象缺失、索引永久失败（importer.go:124-132）。
  6. 【P3】验证语义只做"两边一致"不做"数据确实存在"：key 构造错误等系统性故障时 copy 全量跳过、verify 全通过。
- 已排除：data_migration 单 scope 唯一部分索引（000002 SQL:22）防并行迁移；admin token 保护；session key 构造（session_principal_id=runner userID，AppName=Scope.Key("runner") 与 worker 一致）；artifact reserve/publish 状态机与 advisory lock；租户隔离各层（payload filter+SQL 二次校验+baseIDs 白名单）未见可复现越权。
- 框架源码解压在 %TEMP%\agent-redis、%TEMP%\agent-postgres（session/redis@v1.11.0、session/postgres@v1.11.0 zip）。

## 逐条探讨后的最终修正（第五轮，用户反驳，已达成共识）
- A1：接受收窄。四套里 execution 绑 session-lane/outbox、data_migration 绑 drain+激活事务，queue.Claim 含 Job/TurnSeq 不能强塞；第四处 SKIP LOCKED 是 dispatch outbox 不是 claim。只抽窄的 lease-renew/worker 编排，不造全局状态机。
- A2：不造泛型缓存基座。关闭对象差异大（COS 只清引用，Session/Qdrant/Memory 真关资源），保持各 resolver 所有权。
- A3：成立且要全覆盖——cosclient factory 同时服务 frameworkcos.NewService 与直连 client，两处 http.Client 均无总超时。
- A4：拆两半——main 内 knowledge/cleanup 的 Execution 构造可共用局部 helper；migration 的 resolveExecution 层次不同（还负责 config/storage 解析）保留。续租循环在补 cleanup 续租时一起收敛。
- A5：撤销。Store 只有 pool 状态、方法已按领域文件分布、消费侧接口已隔离，不是 SQL 复制的直接根因；拆类型不会让 SQL 自动共享。
- B1：原判断错误（混淆"动作幂等"与"任务调度"）。lease 承担多节点调度/重试账本/fencing，删除幂等≠状态机多余。真问题是 cleanup 30s lease 无续租 + 请求无总超时 → 修法：加续租，或删除设小于 lease 的 deadline 后重试。
- B2：改为语义校验不是放松。State bytes.Equal 对不透明状态合理（不批）；Event/Track/Summary 全字段比较过强，应定义稳定 ID/顺序/版本/内容摘要语义投影 + 补 Redis→PG 归一化回归测试。设计要求在 phase-2 设计稿 66 行附近。
- B3：成立于每个 cache miss（非每次调用），同步建 3 索引。移到 collection/generation bootstrap + schema 校验 + 并发保护。"已有索引必报错"无官方代码/文档证据，需本地 Qdrant 实测。
- C1/C2：可删（未对外发布）；C2 删导出包装层保留私有核心，两入口契约不同（通用版不支持 Summary 导入）。
- 最终顺序：1) 修 cleanup lease/HTTP deadline、Qdrant 索引初始化；2) 迁移语义校验+跨 Provider 测试；3) 删 C1、收窄 C2、抽 COS factory；4) 最后仅收敛 index/cleanup 窄租约重复；不拆 Store、不造通用 resolver cache。
